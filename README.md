# うちの在庫

家族で共有できる家の在庫管理アプリ(PWA・ビルド不要)。

- 在庫の一覧: 「置き場所別」「分類別」「すべて」「間取り」をボタンで切り替え(最初は置き場所別。選んだ見かたと、たたんだ見出しは端末ごとに記憶)。見出し(冷蔵庫・食品など)は画面の上に張り付き、タップでたためて、足りない/期限が近い品の数が出ます。上の「ぜんぶ/足りない/期限が近い」を押すとその品だけに絞れます(もう一度押すと解除)。品ごとに「期限切れ・残りわずか・あとN日」を文字つきで表示。＋/−(押すと「元に戻す」が出ます)・検索(ひらがな/カタカナどちらでも)・並び替え(選んだ順は記憶)・期限。PCでは `/` で検索、`n` で追加。画面下の中央の＋でどの画面からも追加でき、同じ名前は数量に足されます(「続けて追加」で連続登録)
- **間取り**(在庫の「表示のしかた」の4つ目): 自分の家の間取りを、**部屋と収納場所の四角**を置いて作ります(複数階は未対応)。画面は `js/floorplan-ui.js`(使うときだけ読み込み)、データ・計算は `js/floorplan.js`。
  - 空のときは案内カード(「空から作る」/ひな形 1K・2LDK・3LDK・一戸建て)。平面図は横24マス。**部屋をタップ → その部屋の詳細**(収納場所の四角)→ 収納場所をタップで**下から出るシート**(その場所の在庫・−/＋・「＋ここに追加」・「📷バーコードで続けて追加」)。「ここに追加」は、その場所を追加先(**固定**)にして追加画面を開きます。小さな四角は、下の**一覧**(部屋の一覧・収納場所の一覧)からも開けます。
  - **見る/編集**の切り替え。見るモードは動かせません(スクロールも妨げません)。編集モードで、種類のパレットから四角を置く・**なぞって動かす**(指・マウス)・選んだ四角の角と辺の**つまみで大きさを変える**。なぞれない人・キーボード向けに、**←↑↓→で1マスずつ・横縦の＋−ボタン**、四角にフォーカスして矢印キー(Shift+矢印で大きさ)も使えます。隣に当たると止まる/近くの空きにずらします。名前・色・削除は選んだ四角のツールバーから(削除は確認つき)。直後の「元に戻す」で1操作ずつ戻せます。
  - 収納場所・部屋の**名前が、そのまま品目の置き場所(location)の文字列**になります(家の中で一意。重なると「棚(キッチン)」のように補正して知らせます)。名前を変えたら、その場所の品の置き場所も一括で直すか確認します(元に戻せます)。**消しても品は消えず**、「間取りにない置き場所」になります。間取りにない置き場所(と場所が未設定の品)は、平面図の下の案内から、部屋を選んで間取りに置けます。
  - 編集内容は家の `layout` フィールドに保存され、家族に即時共有されます(差分だけ送信。同時に別の部屋を編集しても両方残り、同じ要素は新しいほうが勝ちます。他の人の編集は再読み込みなしで反映、編集中の四角が消された・動かされたときは知らせます)。お試しモードは端末内(`hs-layout`)。Firestore のルールは変更不要です。
  - 編集ダイアログ・追加先の選択シート・取り込み確認の「置き場所」には、間取りの場所が部屋ごとにまとまって出ます。在庫の「置き場所別」の見出しには部屋名が添えられます。
- **追加先(連続追加)**: 追加の画面(手入力・バーコード・レシート/メール/貼り付けの確認・「まとめて追加」)の上に「追加先」バーが出ます。置き場所(例: 洗面所)や分類(例: 食品 / 野菜・果物)を選ぶと、そのあいだに追加する品がその場所・分類に入ります(選ばなかった項目は自動で分類)。在庫一覧の見出しの「＋追加」を押すと、その場所/分類を追加先にして追加できます。優先順位は「品ごとに手で選んだ値 > 追加先 > 自動分類」。登録済みの品や同名の品は数量だけ増え、場所・分類は変わりません。「固定」をオンにすると、閉じても次の追加へ引き継ぎます(オフなら閉じると「おまかせ」に戻る。端末ごとに記憶: `hs-addctx`)。レシート確認では、手で変えていない行が追加先に追従し、「手で変えた行も、追加先にそろえる」で全行に適用できます
- **賞味期限・消費期限**(品目の「くわしく設定」の期限): 日付の手入力、**「📷 写真で読む」**(端末内OCR。写真は保存も送信もしません。初回だけ約34MBをダウンロード)、**「予測で入れる」**、「前回の期限を使う」、「開封した」(開封後の目安)から入れます。
  - 写真は読み取った候補を**必ず確認する画面**を通ります(自動では保存しません)。元の写真を見ながら、日付を1文字ずつ見比べて選びます。製造日・「開封後◯日」は参考表示だけで、期限には採りません
  - 予測は品名から**標準的な賞味・消費期間**を引く目安で、**答えるが控えめで、直せる**ことを安全策にしています。段階は3つ: 予測(確信が高い)・目安・**おおよそ**(実際より短めの日数。パッケージの表示が優先)。**個々のパッケージの表示と同じとは限りません**。一覧は「(予測)」「(目安)」「(おおよそ)」、予測の期限切れは「期限の目安を過ぎています」、おおよその期限切れは「期限の目安を過ぎたかもしれません」と、さらに控えめに出し、おしらせのバッジにも数えません。表示のある期限(手入力・写真) > 前回 > 予測 の順で優先します
  - 「家族」タブの**予測のきびしさ**(きびしい=予測だけ / ふつう=目安まで / ゆるい=おおよそまで。既定は「ゆるい」。端末ごと `hs-expstrict`)に従って、追加するとき期限が空なら自動で予測を入れます(自動入力のオン/オフは `hs-autoexp`)。「予測で入れる」ボタンは設定に関わらず、いちばんゆるい段階まで試します。薬・サプリ・ベビーミルクなど箱に期限が必ず印字されている品(`critical`)は自動では入れず、ボタンを押したときだけ「箱の表示を確認してください」を添えて入れます
  - 「家族」タブの**まとめて予測を入れる**: 期限が未設定で予測できる品を一覧(品名・予測日・段階)で確かめ、チェックで外し、1回の操作で適用します(「元に戻す」つき)
  - **実際に印字された日付を撮る**: バーコードの連続追加の「📷 期限を撮る」(大きなボタン。確認は1タップ)、「まとめて追加」の「📷 期限だけ撮って追加」(① 撮る → ② 品を選ぶ → ③ 保存 → 次の品へ)、「⏰ 期限をまとめて入れる」(期限未設定の品を1品ずつ: 撮る/予測を使う/入力/スキップ。在庫の見出しの「期限なし N」からも入れます)。確認画面は年も大きく表示し、年を補った・月末として扱った候補は目立たせて、選んだ状態にしません
  - 期限を入れた品には、出どころ `expirySrc`('手入力'|'写真'|'予測'|'前回')、種類 `expiryKind`('賞味'|'消費')、起算日(購入日) `expiryFrom`、予測の段階 `expiryLevel`('high'|'mid'|'low'。予測のときだけ。無い旧データは high 扱い)を保存します(空なら保存しません。無印の旧データは「実際の表示」として従来どおり)
  - 「予測の的中率」(家族タブ、端末ごと `hs-expstats`): 予測・前回の期限を実際の日付に直したとき/「合っていた」を押したときの結果を**段階別**に記録します。5件たまってから表示。**実際の精度を確かめるための記録で、精度の保証ではありません**
  - 期限の部品(shelflife.js・expiry-parse.js・expiry-ocr.js)は、使うときに読み込みます(起動時には読みません)
- **おしらせ(かしこい提案)**(端末内の統計・ヒューリスティクスだけで動作。外部AI・API・通信なし、無料・オフライン可):
  数量の増減から使うペースを学習して「あと約N日」を表示、もうすぐ切れそうな品を買い物に表示、最低在庫/買う数のおすすめ、
  重複品の統合、未分類の自動分類(家族が付けた分類を学習+品名辞書)、期限切れの確認、長期未使用の在庫を提案。
  推定なので、記録が少ないうちは外れます(使うほど正確になります)。「今はしない」は端末内に保存されます
- 「買い足しライン」(最低在庫)以下になると「買い物」リストに自動で出る → 「買った」で補充(押し間違いは「元に戻す」)
- 取り込み: **レシート写真**(端末内OCR。文字の位置検出+文字認識の深層学習モデル、動かない端末では Tesseract.js)。初回だけ読み取り用データ約34MBをダウンロードし、以降は端末内に保存して通信なしで動きます/ **Gmailの注文確認メール**(Amazon・楽天)/ **テキスト貼り付け**
  - 取り込み前に必ず確認画面で名前・数量を直せる。同名品は数量を加算。Gmailは取り込み済みを自動で除外
  - レシートは「カメラで撮る」「アルバムから選ぶ」から。確認画面の上に**撮った写真が固定表示**され(開閉・拡大・全画面でピンチ可)、見ながら直せます。品名が文字化けらしい行・金額が極端な行は黄色(⚠)で強調され、「要確認 N件」ボタンで順にジャンプ。差額は大きく表示し、読み落としは「その他」として足して検算を合わせられます(「その他」は在庫には登録しません)
  - 読み取りが失敗・60秒を超えた・品目が0件のときは、エラーにせず**写真を見ながら入力する画面**に切り替わります(読み取り中の「やめる」でも同じ)。「次へ」キーで 品名 → 金額 → 次の行 と進めます
  - 直した名前は端末内(localStorage の `hs-fixmap`、最大300件)に学習し、次から同じ崩れ方を自動で直します(「前回の修正を適用」と表示)。家族タブの「修正の学習をリセット」で消せます。写真は端末のメモリ上だけで扱い、保存も送信もせず、確認を閉じると破棄します
- 家族共有: Firebase(Google ログイン + Firestore リアルタイム同期)。家族コードで参加(「家族」タブから、誘いのリンク(`?join=コード`)を送れます。開いてログインすると参加画面にコードが入ります)。データはCSV/JSONで書き出せます
- `js/config.js` が空のままなら、この端末だけで動く「お試しモード」

## セットアップ(共有を使う場合)

1. [Firebase コンソール](https://console.firebase.google.com/)でプロジェクト作成(Spark=無料でOK。Storage は使わない)
2. Authentication → Sign-in method で **Google** を有効化。承認済みドメインに公開先(例 `<ユーザー名>.github.io`)を追加
3. Firestore Database を作成し、`firestore.rules` の内容をルールに貼って公開
4. プロジェクト設定 → ウェブアプリ追加 → 表示された設定を `js/config.js` の `firebaseConfig` に貼る
   (この値は公開されても問題ない設計。守っているのはルール)
5. (Gmail連携) Google Cloud Console の同プロジェクトで OAuth クライアントID(ウェブ)を作成し、
   承認済み JavaScript 生成元に公開URLを登録 → `googleClientId` に設定。
   OAuth同意画面は「テスト」のまま、テストユーザーに家族のGmailを追加すれば審査不要
6. GitHub Pages(Settings → Pages → main / root)で公開 → iPhone は Safari で開いて「ホーム画面に追加」

## バーコードと商品名の検索
バーコード(EAN-13・EAN-8・UPC-A)を読み取ると、番号の種類で調べ先を振り分けて商品名を出します(登録時に、その番号が品目に付き、次回からは検索せずに出ます)。
- 日本の商品(45・49 始まり): 楽天市場 → Open Food Facts / Open Beauty Facts / 雑誌(491)は楽天 / 本(978・979)は openBD → Google Books。海外の番号は Open *Facts 系が先
- **店ごとのバーコード**(02・20〜29 始まり=量り売り・店内加工品など)、クーポン、本の2段目(191・192)は、外部に問い合わせず、その旨を案内します(名前を入れれば次から覚えます)
- 見つからないときは理由を出し、**「パッケージの文字から名前を読み取る」**(端末内OCR。写真は保存も送信もしません。初回だけ約34MBをダウンロード)で、商品名らしい行を最大3つ候補に出します
- 検索結果は端末内(localStorage)に保存します(見つかった名前は90日、見つからなかった結果は1日。最大300件)。楽天は1秒以上あけて呼び、429/503は1回だけ待って再試行します
- 読み取れない形式: GS1 DataBar(生鮮・値引きシール)、UPC-E(iPhone のブラウザの読み取り部品では読めない)、QR・Code128。番号の手入力(8・12・13・14桁。UPC-E・GTIN-14 は自動で変換)は使えます

日用品を出すには楽天の設定が必要です(なくても動きますが、日本の日用品は見つからないことが多くなります):
1. https://webservice.rakuten.co.jp/ でアプリを登録し、`applicationId` と `accessKey` を取得
2. アプリの「WebサイトURL」に公開URL(`https://<ユーザー名>.github.io/`)を登録(未登録だと403になります。その場合は「見つからない」ではなく検索対象外として扱い、結果を保存しません)
3. `js/config.js` の `rakutenApi` に貼る
※ Yahoo!ショッピングAPIはブラウザからの呼び出し(CORS)を許可していないため、サーバー経由が必要で未対応です。

## 注意

- Amazon に公式APIは無いため、注文確認メールの本文を解析しています。メール書式が変わると拾えないことがあるので、確認画面で直してください(解析は `js/parse.js` の `parseOrderMail`)
- 日本語レシートのOCRは精度が高くありません(特に品名の誤読が多く、金額と合計のほうが当たりやすい)。写真は明るく真上から撮ると改善します。検算が合わないときは、設定を変えて最大6回読み直すため、1枚に数十秒かかることがあります
- 写真・メール本文は保存しません。保存されるのは品目データだけです
